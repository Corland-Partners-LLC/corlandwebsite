# Corland Partners Website

Production-ready Next.js (App Router + TypeScript + Tailwind CSS) rebuild of
the Corland Partners marketing site — a faith-based "Kingdom Business"
consulting and development firm.

This is the completed rebuild: project scaffold, design tokens, the full
content data layer, shared components, every route (with real, verbatim
copy), the contact API route, SEO metadata/structured data, and Docker
packaging have all been implemented and QA'd.

`AGENTS.md` and `CLAUDE.md` at the repo root are auto-generated by Next.js
itself (regenerated by `next dev`/`next build`) and just point coding
agents at the framework's bundled docs in `node_modules/next/dist/docs/` —
they aren't project documentation and can be ignored/left as-is.

See [`DESIGN_SYSTEM.md`](./DESIGN_SYSTEM.md) for color/font/spacing tokens.

## Tech stack

- Next.js 16 (App Router), TypeScript, Tailwind CSS
- ESLint + Prettier (with `prettier-plugin-tailwindcss`)
- Typed content layer under `content/` (no CMS yet — plain TS modules)

## Install

Requires Node.js 20+ and npm.

```bash
npm install
```

## Run locally (development)

```bash
npm run dev
```

Open [http://localhost:3000](http://localhost:3000). The dev server has fast
refresh — edits to anything in `app/`, `components/`, or `content/` show up
immediately.

## Build for production

```bash
npm run build   # compiles, type-checks, and statically generates every route
npm run start   # serves the production build locally on http://localhost:3000
```

Both commands must run clean (no type errors, no failed pages) before
shipping. `npm run lint` should also be clean.

## Scripts

## Environment variables

Copy `.env.example` to `.env.local` and fill in values as needed:

- `NEXT_PUBLIC_SITE_URL` — canonical site URL, used for metadata/sitemap/
  robots generation (see `lib/seo.ts`, `app/sitemap.ts`, `app/robots.ts`).
  Defaults to `https://www.corlandpartners.com` if unset, so a local/dev
  environment will still build without this set, but real canonical URLs,
  the sitemap, and Open Graph tags won't be correct until it points at the
  real deployed domain.
- `RESEND_API_KEY` / `RESEND_EMAIL_FROM` — required for the contact form
  (`app/api/contact/route.ts`) to actually send email via
  [Resend](https://resend.com). `RESEND_EMAIL_FROM` must be an address on a
  domain verified in your Resend account. Submissions are emailed to the
  address in `content/company.ts` (`company.email`), with the sender's own
  address set as the reply-to, so replying goes straight back to them. If
  either variable is missing, the form still validates input normally but
  responds with a clear error instead of a false "sent" success.

None of these variables are required for `npm run dev`/`npm run build` to
succeed — they only affect metadata correctness and whether the contact
form can actually send email.

## Docker

```bash
docker compose up --build
```

This builds a multi-stage, standalone Next.js production image
(`next.config.ts` sets `output: "standalone"`, so the final image only
contains the minimal server bundle plus `public/` and `.next/static`, not
`node_modules`) and serves it on port 3000. To pass environment variables
through, either export them in your shell before running compose or add a
local (untracked) `.env` file — `docker-compose.yml` reads
`NEXT_PUBLIC_SITE_URL`, `RESEND_API_KEY`, and `RESEND_EMAIL_FROM` from the
environment with the same defaults as above.

To build the image without compose:

```bash
docker build -t corland-website .
docker run -p 3000:3000 corland-website
```

## Deployment

This project isn't tied to a specific host. It runs anywhere that can either
(a) run the Docker image above, or (b) run a standard Next.js Node server
(`npm run build && npm run start`) — e.g. a VPS, a container platform, or a
Next.js-aware host. There is no serverless-specific configuration; if
deploying to a platform that prefers its own build output format instead of
the standalone Docker image, remove `output: "standalone"` from
`next.config.ts` and follow that platform's normal Next.js deployment guide.
Whichever host is chosen, set `NEXT_PUBLIC_SITE_URL` to the real production
domain so canonical URLs, the sitemap, and Open Graph/Twitter metadata are
correct.

## How to edit content

All page copy lives in typed TypeScript modules under `content/`, not in
the page files themselves. This keeps every `app/**/page.tsx` focused on
layout while the words live in one place per topic:

- `content/company.ts` — company name, address, phone/email, booking link,
  hero copy, mission statement/quote, About paragraphs, and other
  site-wide strings pulled into multiple pages (header, footer, hero,
  About, CTA sections).
- `content/pillars.ts` — the four Business Pillars (Organizational,
  Operational, Financial, Marketing & Sales models): slug, title, teaser
  (used in cards), and the full body copy shown on each pillar's detail
  page.
- `content/services.ts` — the seven services (Organizational Health,
  Marketing Assistance, Leader Development, Website Development, Sales
  Team Training, Purchasing Power, Banking Relationships): slug, title,
  and description.
- `content/faq.ts` — the FAQ question/answer pairs shown on both the
  homepage's FAQ section and the standalone `/faq` page.
- `content/impact.ts` — the "Triple Bottom Line" (Kingdom / Social /
  Financial Impact) copy used on the homepage and About page.

To change any wording, edit the relevant string in the matching `content/
*.ts` file — no need to touch a component or page file. To add a new
pillar/service/FAQ entry, add an object to the corresponding array
following the existing shape (each array's `type` export documents the
required fields), then add a matching route file under `app/business-
pillars/<slug>/page.tsx` or `app/services/<slug>/page.tsx` if it's a new
detail page (copy an existing sibling page as a template — they're
intentionally near-identical). Also add the new route to `app/sitemap.ts`
and to the nav lists in `components/Header.tsx`/`components/Footer.tsx`
if it should appear there.

## How to replace/add images

The real Corland Partners logo lives at `public/images/logo/`:

- `corland-partners-logo-horizontal.png` — icon + wordmark + tagline, transparent background. Used in `components/Header.tsx`.
- `corland-partners-mark.png` / `corland-partners-mark-square.png` — icon mark only, transparent background. Used in `components/Footer.tsx`, `app/icon.png`, and `app/apple-icon.png` (Next.js's file-convention favicon/apple-touch-icon, auto-linked in `<head>` — no manual `<link>` tags needed).
- `corland-partners-logo-stacked.png` — icon + stacked wordmark, transparent background. Not currently used, kept for future placements (e.g. a square social card).
- `corland-partners-logo-wide.jpg` — full wide lockup on a white background. Not currently used.

Beyond the logo, there are still **no real photography assets in this project** — every other visual is a solid color, a CSS gradient, or hand-built inline SVG (the decorative diamond motif in `components/Hero.tsx`, icon glyphs, etc.), by design, so the site never shipped with placeholder stock photography.

To add real photography or other raster images:

1. Put the file in `public/images/` (create the folder if it doesn't
   exist yet — anything under `public/` is served as-is from the site
   root).
2. Follow the content-based naming convention already used elsewhere in
   this project, e.g. `kingdom-impact.jpg`, `organizational-pillar.jpg`,
   `leland-headshot.jpg` — a short, descriptive, kebab-case name that says
   what the image is, not where it's used.
3. Reference it with Next's `<Image>` component (`next/image`) from
   `"next/image"`, e.g.:

   ```tsx
   import Image from "next/image";

   <Image
     src="/images/kingdom-impact.jpg"
     alt="Describe what's actually in the photo"
     width={1200}
     height={800}
   />;
   ```

   Always give it a real, non-empty `alt` unless the image is purely
   decorative, in which case use `alt=""` explicitly (never omit `alt`).
4. If the image is genuinely decorative (no informational content), you
   can instead inline it as SVG the way `components/Hero.tsx` does, with
   `aria-hidden="true"` and no `alt`.

## SEO configuration

- `lib/seo.ts` exports `pageMetadata()`, a shared helper every `page.tsx`
  calls to build its `Metadata` export (title, description, canonical URL,
  Open Graph, Twitter card) from one small object, so per-page SEO fields
  stay consistent instead of being hand-rolled per route. It also exports
  `serviceJsonLd()`, used by each service detail page to emit `Service`
  JSON-LD (name, description, provider) in a `<script
  type="application/ld+json">` tag.
- `/faq` additionally emits its own `FAQPage` JSON-LD directly in
  `app/faq/page.tsx` from the `content/faq.ts` data, so search engines can
  render FAQ rich results.
- `app/sitemap.ts` and `app/robots.ts` generate `/sitemap.xml` and
  `/robots.txt` from the same route list, using `NEXT_PUBLIC_SITE_URL` for
  absolute URLs.
- `NEXT_PUBLIC_SITE_URL` (see **Environment variables** above) is the
  single source of truth for the site's canonical domain across all of the
  above — set it in production so metadata, the sitemap, and structured
  data all point at the real URL instead of the placeholder default.

## Project structure

- `app/` — routes (App Router)
- `components/` — shared UI components
- `content/` — typed content data (company info, pillars, services, FAQ, impact)
- `lib/` — shared utilities (SEO metadata/JSON-LD helpers)
- `public/` — static assets (currently just the logo — see **How to
